# 秒杀商城面试讲解

## 一分钟项目介绍

我做了一个基于 Spring Boot 的秒杀商城后端，使用 MySQL 保存商品、活动和订单，Redis 保存活动的快速库存和已参与用户，RabbitMQ 异步处理订单。用户登录后拿到 JWT，提交秒杀请求时服务端从令牌识别用户身份。Redis Lua 脚本原子地检查重复购买和剩余库存，并完成预扣；预扣成功后订单消息发送到 RabbitMQ，接口返回 `202 Accepted`。消费者再用 MySQL 事务和条件库存更新创建订单。这样把高峰请求的快速拦截和较慢的数据库写入分开处理。

## 一次下单的完整链路

1. 用户注册、登录；密码以 BCrypt 哈希保存，登录成功后取得 JWT。
2. 秒杀接口验证活动、商品和活动时间，并从 JWT 中取得用户 ID。
3. Redis 执行 `seckill-reserve.lua`：检查用户是否重复参加、检查库存、扣减 Redis 库存并记录用户。这些动作在同一个 Lua 脚本中完成。
4. 服务把订单消息发到 RabbitMQ，并等待发布确认；请求返回 `202`，表示已受理，订单仍在处理中。
5. RabbitMQ 消费者调用 MySQL 事务：用 `stock > 0` 的条件更新扣减数据库库存，再插入订单。
6. 用户查询订单状态；`PROCESSING` 表示后台尚未完成，`CREATED` 表示订单已经写入数据库。

## 关键设计点

- **Redis Lua**：把库存判断、扣减和用户去重合并为原子步骤，减少并发下重复读到同一份库存的风险。
- **RabbitMQ**：把秒杀请求受理和数据库落单拆开，降低请求线程直接承受数据库写入峰值的压力。
- **MySQL 条件更新和唯一约束**：作为持久化层的最后保护，避免数据库库存低于零和同一用户重复创建活动订单。
- **失败处理**：RabbitMQ 发布失败时尝试释放 Redis 预扣；消费者遇到可预期的业务拒绝时释放预扣；基础设施异常交给重试，最终进入死信队列供排查。
- **认证**：密码使用 BCrypt；订单接口从 JWT 获取用户 ID，不信任客户端传入的用户 ID。

## 已完成的手动并发验证

在本机 Docker Redis、RabbitMQ 和 MySQL 环境中，为独立测试活动准备了 10 个不同账号，并从 PowerShell 并发提交 10 个秒杀请求。之后逐个查询订单状态，10 个状态均为 `CREATED`；活动库存从 100 变成 90。

这证明本次 10 个请求都完成了下单，库存扣减数量与订单数量相符。它是小规模并发功能验证，不是系统容量或性能基准测试：本次没有可靠采集平均响应时间、P95 响应时间、吞吐量或最大可承受并发数。面试时应如实说明，不要把 10 个并发请求说成百万级压测。

## 自动化测试

`SeckillServiceTest` 覆盖正常受理、重复用户和库存不足三个服务层分支。运行 `mvn test` 后 Maven 输出 `BUILD SUCCESS`，表示当前自动化测试阶段通过。测试通过 Mockito 隔离外部依赖，不会连接 MySQL、Redis 或 RabbitMQ；因此它不替代真实中间件环境下的集成测试。

## 常见面试问题

### 为什么 Redis 扣库存后还要 MySQL 再扣一次？

Redis 用于快速拦截并发请求和预扣；MySQL 是订单与库存的持久化数据源。数据库端仍使用带库存条件的更新和唯一约束，防止 Redis 状态和数据库约束之外的异常造成超卖或重复订单。

### 为什么接口返回 202 而不是直接返回下单成功？

接口只确认消息已被接受并交给后台处理。消费者异步写入订单后，用户再通过订单状态接口确认最终结果，因此不能把 `202` 解释为订单已落库。

### Redis 和 MySQL 如何保证强一致？

当前实现没有跨 Redis、RabbitMQ、MySQL 的分布式事务。发布确认、消费者重试、死信队列、预扣补偿和数据库约束处理了常见失败，但进程在预扣和消息发送之间突然退出等情况仍可能需要对账。后续可以用 Outbox、事务消息或库存对账完善。

### 目前压测能说明什么？

只验证了 10 个不同用户同时请求时，本地环境最终创建了 10 个订单，库存从 100 降到 90。它不能推导生产环境吞吐量或最大并发能力；正式性能测试还要记录测试环境、并发数、持续时间、吞吐量、平均和 P95 响应时间、错误率，并观察应用、数据库和消息队列资源。
